# ADR-001: 采用 Modular Monolith 而非微服务

## 状态
已采纳

## 背景

Drama Factory 平台在 2024 年初立项时，核心团队规模为 1-3 人全栈工程师。平台需要同时支撑两条垂直业务线（InvestMind / EduStar），并快速验证 AI 产品的市场需求。

当时面临的核心约束：

1. **人力约束**：3 人团队中没有专职 DevOps，每个人需要同时负责前端、后端和 AI 功能开发。微服务架构意味着每个服务都需要独立的 CI/CD、容器编排、服务发现和跨服务追踪——这些运维工作会吞噬大量开发时间。
2. **迭代速度**：AI 产品早期需要高频修改 Prompt、调整工作流、重构数据模型。如果 MemoryOS 和 AgentOS 是两个独立服务，每次接口变更都需要同步修改两侧代码并协调部署，摩擦成本极高。
3. **领域边界不清晰**：InvestMind 的研究工作台和 EduStar 的课程工厂都需要调用 AgentOS，早期难以判断这两条业务线的边界在哪里，过早拆分会导致错误的服务边界难以纠正。
4. **成本压力**：微服务通常需要 Kubernetes 集群或至少多台服务器，而单体应用可以跑在一台 $20/月的 VPS 上，或通过 Railway/Render 一键部署。

## 决策

采用 **模块化单体架构（Modular Monolith）**：整个后端作为一个 FastAPI 进程部署，但内部严格按照模块边界组织代码。目录结构反映逻辑分层：

```
backend/app/
├── platform/          # AI 平台层（内部模块）
│   ├── memory/        # MemoryOS
│   ├── agent/         # AgentOS
│   ├── avatar/        # AvatarOS
│   └── percept/       # PerceptOS
├── verticals/         # 业务垂直层（内部模块）
│   ├── invest/
│   └── edu/
└── workers/           # 异步 Worker（独立进程，但共享代码库）
```

模块间通过 Python 函数调用通信，**禁止跨模块直接访问数据库**（每个模块只能调用自己的 repository 层），为未来拆分保留边界清晰度。

## 选项对比

| 选项 | 优点 | 缺点 |
|------|------|------|
| **微服务架构** | 独立扩展、技术栈自由、故障隔离、组织扩展性好 | 运维复杂（K8s/服务网格）、网络延迟、分布式追踪难、需要专职 SRE、初期开发摩擦大 |
| **模块化单体** | 开发效率高、零运维开销、代码重构容易、单进程调试、为拆分保留边界 | 无法独立扩展模块、单点故障风险、大规模并发受限、技术债如果边界不守会退化成泥球 |
| **纯单体（Big Ball of Mud）** | 最简单、最快上线 | 无边界意识、重构成本极高、技术债在规模增长后几乎无法偿还 |
| **服务网格（Istio + K8s）** | 最高可观测性和韧性 | 团队规模不足 10 人时是过度工程，学习曲线陡峭 |

## 结论

选择模块化单体的核心逻辑是：**在不牺牲未来灵活性的前提下，最大化当前迭代速度**。

关键决策依据：
- **Sam Newman 的"先建单体"原则**：在领域边界明确之前拆分服务，会导致错误的服务边界，后续重构成本远高于直接从单体拆分。
- **保留拆分路径**：模块化设计意味着当某个模块（如 AvatarOS）需要独立扩展时，可以将其抽取为独立服务，只需将函数调用改为 HTTP/gRPC 调用，而不需要重构业务逻辑。
- **Worker 作为拆分预演**：`avatar_worker.py` 和 `feed_worker.py` 已经以独立进程运行，共享代码库但独立部署，这是介于单体和微服务之间的务实中间态。

拆分触发条件（预设）：当团队超过 8 人，或单个模块的 CPU/内存需求超过其他模块 5 倍时，触发该模块的微服务化评估。

## 后果

**正面影响：**
- 本地开发只需 `docker compose up`，新人上手时间从天级缩短到小时级
- 跨模块重构（如修改 MemoryOS 接口）可以在单次 PR 中原子完成，不存在版本兼容问题
- LangSmith 追踪跨越整个请求链路，无需分布式 Trace ID 拼接

**需要接受的负面影响：**
- MemoryOS 和 AgentOS 无法独立扩展——当 Agent 调用量激增时，Memory 模块也会被迫扩容，存在资源浪费
- 必须靠代码规范（Code Review + Lint 规则）强制维护模块边界，如果团队不自律会退化为泥球单体
- 一个模块的内存泄漏会影响整个进程，需要严格的资源管理

**技术债管理：** 每季度进行一次"模块边界审查"，检查是否有跨模块直接数据库访问或循环依赖，及时偿还架构债务。
